# Как устроены задачи курса

Каждая задача — один файл `content/<модуль>/<NN-название>.md`. Каждый модуль — папка `content/<NN-название>/` с файлом `module.md`.
После любых правок: `node tools/validate.mjs <модуль>` (проверка) и `node tools/build.mjs` (сборка в `data/`).

## Главные правила курса

1. **Только практика из настоящей разработки.** Каждая задача — это кусочек реального приложения: корзина, профиль, статус заказа, уведомление, кэш, платёж. Никаких «найди факториал», «числа Фибоначчи», «площадь треугольника», «проверь, простое ли число», абстрактных `foo/bar`, фигур и животных ради наследования. Арифметика допустима только как часть жизненной задачи (сумма заказа, скидка, остаток на счёте).
2. **Один шаг за раз.** В задаче одна новая идея. Использовать можно только то, что уже было в предыдущих задачах и модулях, плюс новое из этой задачи — и это новое обязательно объясняется в описании.
3. **Плавный рост.** Первая задача модуля — совсем простая «проба» новой темы, дальше понемногу сложнее, последняя — итоговая, где собирается всё из модуля.
4. **Всё на русском** (кроме кода): описания, подсказки, названия тестов, комментарии в коде, тексты, которые печатает программа. Имена переменных, функций и типов — на английском, как в настоящих проектах.
5. **Обращение на «ты», в женском роде**: «ты уже умеешь», «ты объявила», «ты написала». Тон — тёплый, спокойный, как у наставника, который верит в ученицу. Без сюсюканья и без ласковых прозвищ: личные слова добавляет сам сайт (записки и подарки).
6. **Ученица — новичок.** Ни одного термина без объяснения. Короткие предложения. Сначала «зачем это нужно в приложении», потом «как это пишется».

## Среда выполнения

- Swift 6.2.4, Linux, режим языка Swift 5 (по умолчанию). Код — один файл, выполняется сверху вниз, как скрипт (`main.swift`).
- Доступны стандартная библиотека и `Foundation` (только если ученица сама написала `import Foundation`; если задача требует Foundation — в стартовом коде эта строка уже должна быть).
- **Нет** UIKit, SwiftUI, Combine, сети, файлов, ввода с клавиатуры (`readLine`). Сетевые запросы, базы данных и «экраны» имитируются обычными функциями и типами.
- Лимит времени — около 10 секунд на запуск. `Task.sleep` в задачах про конкурентность — не больше 50 мс за раз.
- Верхнеуровневый `await` работает (нужен для тестов асинхронного кода).
- Если задаче нужен режим Swift 6 (строгая проверка конкурентности) — в шапке `swiftArgs: -swift-version 6`.

## Формат файла задачи

````markdown
---
title: Короткое название (до 60 символов)
concept: Какая тема Swift отрабатывается (коротко)
---

## @description

### Контекст
2–5 предложений: что за приложение, что за экран или функция, кто и о чём просит (тимлид, дизайнер,
менеджер, тикет из трекера). Должно читаться как настоящая рабочая задача.

### Новое в Swift
Объяснение новой идеи с нуля: зачем она нужна, как записывается, небольшие примеры кода.
Примеры — на ДРУГИХ данных, не тех, что в задаче: объяснение не должно быть готовым решением.
Если нового нет (итоговая задача) — раздел называется «### Что пригодится» и кратко напоминает нужное.

### Задача
Нумерованный список точных требований: какие имена объявить, какие типы, какие параметры и метки,
что вернуть или напечатать. Всё, что проверяют тесты, должно быть названо здесь явно и однозначно.

### Пример
Что должно получиться: ожидаемый вывод программы или примеры вызовов с результатами.

## @starter
```swift
// Стартовый код: то, что ученица видит в редакторе.
// Готовые данные, заготовки, комментарии-подсказки «напиши здесь…».
```

## @solution
```swift

```

## @output
```
Точный ожидаемый вывод программы (необязательный раздел)
```

## @tests
```swift

__eq("Название проверки по-русски", total(price: 100, count: 2), 200)
```

```swift
let total = 1200
```
```

## @rules
- must: /\bguard\b/ :: В этой задаче нужно использовать `guard` — в коде его не видно.

## @hint1
Путь решения словами, подробно, БЕЗ кода (только упоминания имён в `обратных кавычках`).

## @hint2
Слова + ключевой фрагмент кода (не всё решение).

## @hint3
Почти готовое решение с 1–3 пропусками (`___`) и наводящей фразой про то, что в них вписать.

## @hint4
Короткое вступление, затем отдельной строкой:

{{solution}}

А после — подробный разбор: что делает каждая часть, ПОЧЕМУ именно так, какие ошибки типичны.
````

### Как работает проверка

Задача считается решённой, когда выполнено всё из заданного:

1. Код компилируется и не падает.
2. **`@output`** — вывод программы совпадает с ожидаемым (пробелы в конце строк и пустые строки в конце не важны, всё остальное — точно).
3. **`@tests`** — все проверки прошли.
4. **`@rules`** — все правила соблюдены.
5. **`@case`** — для каждого сценария входные данные в коде ученицы **подменяются**, программа запускается заново, и вывод сравнивается с ожидаемым. Так ловится «подгонка под ответ», когда вместо вычисления напечатан готовый текст.

Нужен хотя бы один способ: `@output` или `@tests`.

### Помощники для `@tests`

```swift
__eq("название", получено, ожидалось)            // сравнение любых Equatable-значений
__eq("название", получено, ожидалось, hint: "…")  // hint покажется ученице, если проверка не прошла
__ok("название", условие)                         // условие должно быть true (тоже есть hint:)
__near("название", 0.1 + 0.2, 0.3)                // сравнение Double с погрешностью (eps: 0.001)
__pass("название")                                // засчитать проверку вручную
__fail("название", "что пошло не так")            // провалить проверку вручную (например, в catch)
```

- Название проверки — по-русски, человеческим языком: что проверяется и на каких данных («Скидка 10% для заказа на 2000 ₽»).
- `hint:` — подсказка «что, скорее всего, не так» для неочевидных случаев (границы, пустые данные).
- Проверяй несколько случаев: обычный, граничный (ровно на границе условия), «пустой» (пустой массив, nil, ноль).
- Кортежи не `Equatable` — сравнивай их поля по отдельности.
- Для функций, бросающих ошибки, используй `do/catch` c `__pass` / `__fail`.
- В тестах можно писать любой Swift, включая `await`, вспомогательные типы и функции. Имена своих помощников начинай с `__t_`, чтобы не столкнуться с кодом ученицы.
- Если нужно проверить то, что код *печатает* изнутри функции, — лучше измени задачу так, чтобы функция *возвращала* значение. Вывод всей программы проверяется через `@output`.
- Тесты выполняются после всего кода ученицы. Если её код верхнего уровня что-то печатает, это не мешает.

### Сценарии `@case` (для задач без функций)

Пока функции не изучены (модули 1–5), логика пишется прямо на верхнем уровне и работает с «входными данными» — константами в начале стартового кода. Чтобы проверить код на других данных, добавь сценарии:

- в первом блоке — объявления, которые заменят одноимённые объявления в коде ученицы (строка целиком);
- во втором — ожидаемый вывод.

Требования: каждое входное объявление в стартовом коде и в решении занимает **одну строку** и стоит на верхнем уровне; в стартовом коде входные данные отделены комментарием `// Входные данные (их подменяет проверка — не переименовывай)`. Сценарии должны покрывать все ветки логики и границы. В `@case` тесты не выполняются — сравнивается только вывод.

### Правила `@rules`

`must` / `mustnot` — регулярное выражение JavaScript, которое должно (не должно) находиться в коде **без комментариев**. `mustraw` / `mustnotraw` — то же по исходному тексту вместе с комментариями. После `::` — сообщение ученице. Используй, когда важен *способ* решения (применить `guard`, не использовать `!`, объявить через `let`). Регулярки пиши осторожно и терпимо к пробелам.

### Требования к качеству

- **Описание — подробное** (от 900 символов, обычно 1500–3000): прочитав его, ученица точно понимает, что делать и зачем.
- **Стартовый код** не должен проходить проверку. Он может не компилироваться (например, пустая функция без `return`), но лучше, чтобы первая же проверка давала понятное сообщение.
- **Решение** — без предупреждений компилятора, идиоматичное, такое, какое не стыдно показать на код-ревью.
- **Тесты нельзя обойти** очевидной «заглушкой» (вернуть константу, напечатать готовый текст).
- **Подсказки идут по нарастающей**: 1 — только слова; 2 — фрагмент; 3 — почти всё; 4 — полное решение и разбор «как и почему» (от 400 символов помимо кода). В подсказке 4 обязательно объясни, почему решение устроено именно так, и назови 1–2 типичные ошибки.
- Тексты, которые печатает программа, — живые и правдоподобные: настоящие названия блюд, тарифов, товаров; цены в ₽.
- **Имена.** Единственное имя человека во всём курсе — **Билол** (латиницей `Bilol`, в логинах и почте — `bilol`). Любой названный по имени человек в задаче — клиент, коллега, владелец профиля, отправитель, контакт, исполнитель песни — это Билол. Никаких других имён, фамилий и «именных» ников (никаких Анна, Тимур, Марина, `anna@...`, `timur_k`). Если в задаче нужно несколько разных людей или аккаунтов, имя получает только один из них, остальные обозначаются без имён: по роли или родству (мама, сестра, подруга, коллега, курьер, бариста), безымянными никами и логинами (`coffee_lover`, `night_owl`), группы и проекты — названиями без имён людей («Северный ветер», «Лунный свет»). «Билол» — мужское имя: склоняй его (Билола, Билолу, Билолом, о Билоле) и согласуй глаголы и прилагательные в мужском роде.
- **Удобно набирать.** В текстах, которые ученица должна напечатать сама (то, что сравнивается с `@output` и в тестах), используй только символы, которые легко набрать на обычной клавиатуре: буквы, цифры и `. , : ; ! ? - ( ) % + = /`. Не используй « », длинное тире —, ₽ (пиши `руб.`), №, …, эмодзи — если только они не даны готовыми в стартовом коде.
- **Предсказуемый вывод.** Порядок элементов в словарях и множествах случаен — перед выводом и сравнением сортируй. Результаты параллельных задач собирай в предсказуемом порядке. Никаких текущих дат, времени и случайных чисел в проверяемом результате.
- Названия файлов и папок — латиницей: `03-delivery-cost.md`.

### Файл модуля `module.md`

```markdown
---
title: Название модуля
project: Название проекта-приложения, над которым идёт работа в модуле
emoji: ☕
summary: Одно предложение о том, чему учит модуль
---
Вступление (2–4 абзаца, от 200 символов): что за проект, какая у ученицы роль в команде,
чему она научится и где это пригодится в настоящих приложениях.
```

### Полезные команды

```bash
node tools/validate.mjs 03-conditions                   # проверить модуль
node tools/validate.mjs content/03-conditions/02-x.md   # проверить одну задачу
node tools/try.mjs content/03-conditions/02-x.md attempt.swift   # прогнать свой код через проверку задачи
node tools/try.mjs content/03-conditions/02-x.md --starter       # что увидит ученица, нажав «Проверить» сразу
node tools/build.mjs                                    # собрать data/ для сайта
```

Для проверок нужен Docker с образом `swift:6.2` — тот же компилятор, что использует сайт.
